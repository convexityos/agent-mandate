# `am/1` conformance vectors

Chain in, verdict out. These files let an implementation in any language check
itself against the Agent Mandate Protocol without reading the reference
TypeScript.

A spec with an executable conformance suite is a standard. One without is a
document.

## Files

| File | What it covers |
|---|---|
| `index.json` | Manifest: suites, counts, the fixed `now` |
| `keys.json` | The five test keys, as RFC 8032 seeds |
| `chain.json` | §7 chain verification and §8 request coverage |
| `caveats.json` | §6 the lattice — `narrows`, `meet`, validation |
| `uri.json` | §6.4 canonicalization and pattern containment |

Everything is generated by [`test/vectors.build.ts`](../test/vectors.build.ts)
and regenerated with `npm run vectors`. The files are committed because they are
the artifact you test against, and a generator nobody has run is not a
conformance suite.

## The rule that makes them worth anything

**Every expectation was written by hand from the specification.** None of it was
recorded from what the reference implementation happens to do.

That distinction is the whole point. Vectors captured by running an
implementation and snapshotting its output cannot disagree with it — they encode
its bugs as conformance requirements, and then certify every future
implementation for faithfully reproducing them.

[`test/vectors.test.ts`](../test/vectors.test.ts) runs all of these against the
reference implementation. When a hand-written expectation and the implementation
disagree, exactly one of them is wrong, and finding out which is the exercise.
Writing this suite turned up six such disagreements. All six were errors in the
vectors, and two of them were interesting enough to keep as vectors in their own
right — see `uri/encoded-slash-is-not-a-separator` and
`chain/child-cannot-outlive-parent`.

## Running them

Every vector has `id`, `spec`, `title`, `why` and `expect`. The `why` is not
decoration: when a vector fails in your implementation it is the sentence that
tells you which assumption of yours is wrong, which a bare expected-vs-actual
never does.

### `chain.json`

```jsonc
{
  "id": "chain/grandchild-redeclares-settle",
  "tokens": ["eyJ...", "eyJ...", "eyJ..."],   // compact JWS, root first
  "request": { "resource": "...", "amount": { "cur": "USD", "amt": "0.02" } },
  "now": 1800000000,                           // unix seconds; use this, not your clock
  "trustedRootIssuers": ["did:key:z6Mk..."],
  "presenterJkt": "...",                       // optional; §7 step 9
  "expect": { "ok": false, "code": "attenuation_violation" }
}
```

Verify `tokens` against `request` at `now`, trusting exactly the DIDs in
`trustedRootIssuers`. Compare `ok`, and on failure the §15 error `code`. A
positive vector may also carry `effective` — the folded authority — which is
worth checking because acceptance alone does not prove you folded correctly.

### `caveats.json`

`op` is `narrows`, `meet` or `validate`. For `meet`, `expect.result` is the
folded caveat set, or `{"bottom": true}` where the meet is ⊥. ⊥ is a real
lattice element with deliberately no wire representation: a fold that reaches it
must fail validation rather than serialize.

### `uri.json`

`op` is `canonicalize` (with `expect.output`, `null` meaning *reject this URI*),
or `uriSetContains` / `hostSetContains` (with `expect.result`).

### `keys.json`

Each entry has a 32-byte `seedHex`. Derive the Ed25519 public key from it per
RFC 8032 §5.1.5 and you should reproduce the `did` and `jkt` given. If you do
not, your key derivation is wrong and every signature check below will fail for
a reason that has nothing to do with this protocol.

These are published test keys. They are not secret and must never be used for
anything.

## What `am/1-core` means

Passing every vector here means your implementation agrees with the reference on
**stateless verification**: signature and issuance structure, the caveat lattice,
the fold, URI canonicalization and containment, and §8 request coverage.

It deliberately does **not** cover:

- **Ledger consumption state.** `max_total` and `rate` are enforced by walking
  the ancestor path against recorded spend (§10.1–10.2), so a vector would have
  to ship an initial ledger state and an expected one. That is a different and
  larger format, and stateless verification is the part a third party can
  implement independently. A verifier that pretended to enforce a budget would be
  worse than one that visibly does not.
- **Settlement.** Rails, receipts, directives and the three-outcome rule are
  §11–§12 and need a rail to talk to.
- **Step-up and control decisions.** §10.5 and §10.6 are ledger-stateful for the
  same reason.

## Two places the spec is not normative enough

Found by writing these, and worth knowing before you file a bug against your own
code:

1. **§8 rule precedence is unspecified.** When a request violates several
   coverage rules at once — a host outside `aud` *and* outside `resources` — the
   spec does not say which error code wins. The reference checks `aud` first;
   §8's pseudocode lists `resources` first. Every vector here isolates a single
   rule so this ambiguity is never load-bearing. If your implementation returns a
   different code for a request that breaks two rules, you are not
   non-conformant; the spec simply does not say.

2. **Reserved characters stay percent-encoded, and this looks like a bug.**
   `%2E%2E%2F` canonicalizes to `..%2F`, not to a resolved traversal, because
   only *unreserved* characters are decoded — `/` is a reserved delimiter.
   Decoding it would manufacture a path separator the requester never sent, which
   escapes grants rather than enforcing them. `%2E%2E/` — encoded dots, literal
   slash — *does* resolve, and must. Both cases are vectors.
